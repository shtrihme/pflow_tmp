# CLAUDE.md

## Старт сессии: проверь видимость репозитория

**Первым делом** — проверь, публичный ли репозиторий. Вызови `mcp__github__search_repositories` с `query: "repo:<owner>/<repo>"` и `minimal_output: false`, проверь поле `private`.

Если `private: false` — **немедленно предупреди пользователя** до любой другой работы:

> ⚠️ Репозиторий публичный. pflow-проекты содержат конфиденциальную продуктовую стратегию (сегменты, гипотезы, юнит-экономику). Рекомендую сделать его приватным: GitHub → Settings → Danger Zone → Change visibility → Private.

Owner и repo — из `git remote get-url origin` (форматы: `github.com:owner/repo`, `github.com/owner/repo`, прокси `127.0.0.1/.../owner/repo`).

Это **пустой pflow-проект** — в воркспейсе ещё нет `.pflow`/`.sflow` файлов, пользователь только что инициализировал каркас. Роль агента, шпаргалка по DSL и правила «зелёной» модели — в @AGENTS.md.

## Жёсткое правило: MCP first

В воркспейсе подключён MCP-сервер `pflow` (см. `.mcp.json`).

**Перед чтением `.pflow`-файлов через Read/Glob/Grep — обязан использовать MCP-инструменты `pflow_*`.** Read по `.pflow` — только если MCP-срез уже получен и нужно посмотреть точное окружение конкретной строки.

### Если `mcp__pflow__*` инструментов нет (CI / headless-агент без MCP-клиента)

Тот же бандл умеет звать tool напрямую из CLI — без JSON-RPC обёртки:

```bash
node .pflow/mcp/pflow-mcp.cjs tools                                      # список tool'ов + аргументы
node .pflow/mcp/pflow-mcp.cjs tool pflow_scaffold --args '{"entity_type":"канвас","language":"pflow","name":"...","write":true}'
node .pflow/mcp/pflow-mcp.cjs tool pflow_fields   --args '{"entity_type":"услуга"}'
```

`--args` — JSON (валидируется схемой tool'а), воркспейс — cwd или `--workspace <dir>`. Те же tool'ы и аргументы, что у нативного MCP. Зови через Bash.

В пустом проекте основные команды:
- `pflow_overview` — стартовый вызов; в пустом проекте `entity_counts.total = 0` — так подтверждаешь, что ничего не пропустил.
- `pflow_list` — пока вернёт пустой список.
- `pflow_scaffold { entity_type, language, name, write: true }` — создать первую сущность (`language` — `pflow` или `svcflow`, обязателен).
- `pflow_validate` — обязателен после **каждой** правки `.pflow` или `.sflow`.

## Помощь со стартом

Если пользователь говорит **«помоги начать»**, **«помоги создать первый Юнит»**, **«у меня есть стратегия в Notion, преобразуем»** или похожее — действуй как со-проектировщик, не как технический помощник.

**Главный принцип:** сначала **кабинетный ресёрч** (10–30 мин ты сам через `WebSearch`/`WebFetch`), потом сверка с PM, и только потом запись в pflow. Не задавай 5 вопросов про Сегмент/Работу/Сегменты — на старте у PM часто ещё нет ответов, а у тебя есть открытые источники.

**Алгоритм:**

1. **Уточни нишу** (1–2 коротких вопроса, не 5):
   - «Что за продукт / в какой нише, на какую аудиторию, в каком регионе?»
   - «У тебя уже есть наработки (интервью, конкурент-аналитика, цифры) — или будем с открытых источников?»

2. **Кабинетный ресёрч сам через `WebSearch` / `WebFetch`** (если у пользователя нет наработок):
   - **3–5 референтных конкурентов** — сайты, тарифы, обещания. Из этого: будущие `Предложение` / `Услуга` / `Доход` / `Канал`, гипотезы `УТП`.
   - **Отзывы и кейсы** — Яндекс.Карты, 2GIS, Otzovik, App Store, Reddit, профильные форумы. Из жалоб: опровергающие Сигналы на конкурентские Предложения/УТП, признаки `Сегмент`, формулировки `Работа.Когда:`.
   - **Рыночные данные** — Wordstat (Яндекс), статьи в РБК / VC / Habr, отраслевые обзоры. Из этого: `Размер:` Сегмента.
   - **Альтернативные способы** решить ту же задачу (DIY, ничего-не-делать, заместитель) — будущие `Альтернатива`.

3. **Систематизация в pflow** через `pflow_scaffold` с `write: true`. Канонический порядок minimum viable:
   1. **Альтернатива(ы)** — что клиент использует сейчас.
   2. **Сегмент** (с `Описание`, `Размер`, `Ранние` — числа из обзоров, описание из отзывов).
   3. **Работа** (`Когда`/`Хочу`/`Чтобы`/`Но`/`Тип`/`Сегменты` — формулировки из жалоб).
   4. **Канвас** — бизнес-модель: `Канал:` (где конкуренты ловят), `Доход:` с `Цель:` (примерные оценки по рынку). Ценностное предложение — отдельной сущностью **VPC** под каждый Сегмент: `Сегмент:` + `Работы:` (ссылка) + `Альтернативы:` + `УТП:` + одно `Предложение:` со `Статус: гипотеза`. Канвас → VPC через `Канвас.VPC:`.
   5. **Юнит** — точка входа, `Статус: перспективный` / `Валюта:`, ссылается на Канвас и Сегменты.

   После каждого `pflow_scaffold` — обязательный `pflow_validate`.

4. **Все Сигналы первой волны = `Категория: кабинет`** с реальной ссылкой:

   ```pflow
   Сигнал: "пик запросов 'X' — ноябрь" {
     Категория: кабинет
     Источник:  "https://wordstat.yandex.ru/?words=..."
     Дата:      "2026-05-22"
     Подтверждает: [ Сегмент."<имя>" ]
   }
   ```

5. **Сверка с PM** перед глубинными интервью:

   > Вот что нашёл из открытого:
   > - Сегмент «X» (по N клиентов в Y, источник: …)
   > - 3 конкурента: A (УТП: …), B, C
   > - Боли из отзывов: «…», «…», «…»
   > - Альтернативы: …
   > Что совпадает с твоей картиной? Что нужно убрать/добавить из закрытого?

   Жди реакции. **Не двигайся к интервью без согласования.**

6. **Глубинные интервью / валидация** — PM делает сам. Когда подтверждается гипотеза:
   - `Статус:` Предложения с `гипотеза` → `в_работе` → `работает`.
   - Сигналы получают `Категория: эксперт` / `пользователь` / `продажа` / `метрика`.

**Не вываливай всю модель сразу.** Один Сегмент → одна Работа → один Канвас → один Юнит = minimum viable. Расширение — по конкретным запросам.

**Запрет на выдумку.** Сигналы (`Наблюдение`, `Источник`, `Дата`) — **только** если есть реальный источник (URL, скриншот, транскрипт). Кабинетные — открытые ссылки (Wordstat, сайт конкурента, отзыв на 2GIS). Размер Сегмента, цели Дохода — реальные числа или явный плейсхолдер `0`. Полный workflow — в `AGENTS.md`, раздел «Workflow: с чего начать новый продукт».

## Если пользователь хочет посмотреть пример

Предложи создать отдельный репозиторий из шаблона **pflow-starter** — там готовая модель химчистки ковров «Премиум» с 4 PM-кейсами, которую можно потрогать в действии, не засоряя текущий проект.

## Трекинг сессий через GitHub Issues

Issue — живой рабочий лог, а не посмертный отчёт. Создаётся **сразу**, как только понята задача, и дополняется по ходу работы.

**Когда создавать:** после 1–2 уточняющих вопросов, как только цель сессии стала ясна — **параллельно с запуском ресёрча**, не после пуша. Чисто технические правки (опечатка, переименование) — не в ишью.

### Жизненный цикл Issue

**Шаг 1 — сразу при понимании задачи** (параллельно с первым `WebSearch`):
Создай Issue с минимальным телом:

```markdown
## Цель сессии
Одно предложение — что хотим сделать.

## Статус
🔄 в работе
```

**Шаг 2 — после ресёрча** (параллельно с первым `pflow_scaffold`):
Обнови Issue — добавь секцию «Ресёрч»:

```markdown
## Ресёрч
- [источник](URL): вывод — только реальные находки
- ...
```

**Шаг 3 — после git push** (финальное обновление):
Обнови Issue — добавь оставшиеся секции:

```markdown
## Создано / изменено
- `Сегмент "X"` — добавлен, размер N, источник Y
- `Канвас "Z"` — обновлены Каналы
- ...

## Развилки
- Вопрос → Решение (и почему)
- ...

## Открытые вопросы
- ...

## Следующий шаг
Что делать в следующей сессии.

## Статус
✅ готово
```

**Правила:**
- Заголовок: `Сессия YYYY-MM-DD: <цель>` — дата сессии, не создания ишью.
- Обновляй через `mcp__github__issue_write` с `method: update` и `issue_number`.
- Не закрывай ишью — это хроника, не задача.
- Если GitHub MCP недоступен — выведи тело ишью в чат, PM создаст сам.

## Когда модель окрепла — нарративные саммари для web-страницы

Как только в проекте появилось 2-3 Сегмента, Канвас и хотя бы одно Предложение — модель уже можно «рассказать» на web-странице `/r/<owner>/<repo>` в pflow-viewer'е. Каждый аспект (что продаём, кому, какие развилки прошли, что проверять дальше) ждёт LLM-нарратива.

Жизненный цикл narrative-v2 саммари:

1. **`pflow_aspect_v2_status`** — какие из ~20 аспектов missing/stale/fresh.
2. **`pflow_aspect_v2_context { aspect_id, scope }`** — возвращает: `blocks` (структурный compute), `data_sources` (whitelist — не ссылайся за пределы), `sibling_summaries` (соседние для стилевой согласованности), **`prompt`** (контракт стиля ДЛЯ ИМЕННО ЭТОГО слота — что/структура/тон/длина), **`voice`** (общий голос проекта из `.pflow/voice.md`, если есть), `input_hash`.
3. **`pflow_aspect_v2_save { aspect_id, scope, text, input_hash, generated_by }`** — атомарная запись в `.pflow/summaries-v2.jsonl`. Race-free через `input_hash`.

**Иерархия применения стиля:** `prompt` задаёт **что должно быть**; `voice` — **как звучит проект**; `sibling_summaries` — **мимикрия под соседей** при отсутствии voice.

Если пользователь редактирует `.pflow/voice.md` (шаблон с секциями «Аудитория / Тон / Запреты / Форматы» закомментирован внутри) — следуй ему как контракту: это его выбор тона. Не игнорируй и не «улучшай» голос проекта своим вкусом.
