# Справочник сущностей pflow / svcflow

> **Сгенерировано** `scripts/gen-dsl-reference.mjs` из семантических брифов
> (`src/language/scaffold-prompts.ts`). Руками не править — поправь бриф и перегенерируй
> (`node scripts/gen-dsl-reference.mjs`). Те же брифы отдаёт MCP-tool `pflow_guide`.

Каждый блок: **Зачем** (роль) · **Имя** (как назвать, ✓/✗) · **Что писать** (поля) ·
**На чём основываться** · **Антипаттерны**. Имена сущностей — человекочитаемые фразы,
не идентификаторы (см. docs/claude/conventions.md «Имена сущностей — человекочитаемые»).

## pflow — стратегический слой

### Юнит

_Файл: `units.pflow` · keyword: `юнит`_

**Зачем:** контейнер портфеля стратегии. Один Юнит = одна командная единица с одной валютой и набором Канвасов. Если у команды несколько направлений с разной командой/бюджетом — это разные Юниты.

**Имя:** название бизнес-единицы/команды человеческим языком. ✓ «Премиум химчистка» / ✗ «unit1», «Юнит_1».

**Что писать:** Назначение (коммерческий/маркетинговый/продуктовый/экспериментальный), Статус (текущий/перспективный/закрытый), Валюта (default для дочерних Канвасов), списки Канвасов и Сегментов, портфельные Метрики (Выручка_месяц, AOV, Клиентов_месяц, LTV, Расходы_фиксированные — целые числа).

**На чём основываться:** реальная орг-структура (одна команда = один Юнит). Метрики — ТЕКУЩИЕ данные; цели идут в Доходах Канвасов.

**Антипаттерны:** один Юнит на всю компанию с 5+ Канвасами разных типов; цели вместо текущих значений в Метриках; пустые Метрики (если не знаешь — не пиши, не ставь 0).

### Канвас

_Файл: `canvases/<имя>.pflow` · keyword: `канвас`_

**Зачем:** одна бизнес-модель для одного продуктового направления (B2C / B2B / etc). Если для разных аудиторий нужны разные Каналы или Доходы — это разные Канвасы под одним Юнитом.

**Имя:** продуктовое направление + аудитория/ниша. ✓ «Годовая чистка офиса (B2B)» / ✗ «b2b_canvas», «Канвас 2».

**Что писать:** Преимущество (defensible moat одной фразой), Каналы привлечения с unit-economics (CAC/LTV/Конверсия), Доходы и Расходы, BMC-блоки (Партнёры/Ресурсы/Активности/Отношения), Метрики Канваса (AOV, Клиентов_месяц), список VPC[] и Ситуации[].

**На чём основываться:** unit-economics: реальные CAC/LTV каналов; референсные конкуренты для цены; собственные данные для Метрик.

**Антипаттерны:** один Канвас на 3+ Сегмента (тогда нужно столько же VPC); пустое Преимущество; AOV=0 как реальная метрика.

### VPC

_Файл: `vpc/<имя>.pflow` · keyword: `vpc`_

**Зачем:** ценностное предложение per-segment. На каждый Сегмент Канваса — свой VPC. Содержит вложенные Предложения.

**Имя:** обычно «<бренд/линейка> <сегмент>». ✓ «Премиум B2B» / ✗ «vpc2», «ценностное_предложение_1».

**Что писать:** Сегмент (ref), Работы[] (ref), Альтернативы[] (что делает рынок), УТП (одна короткая мысль про дифференциацию), Blue Ocean ERRC (Убрать/Снизить/Поднять/Создать — последние два через Результат-ссылки), Предложение(я) со Статус (гипотеза/в_работе/работает) и Покрытие.

**На чём основываться:** интервью с целевым сегментом, конкурентный анализ для Альтернатив, ODI Outcomes для Поднять/Создать в ERRC.

**Антипаттерны:** УТП «лучший сервис» (бессодержательно); Предложение со Статус: работает без подтверждающего Сигнала и без защищающей твёрдой Премиссы.

### Сегмент

_Файл: `segments/<имя>.pflow` · keyword: `сегмент`_

**Зачем:** кому продаём. Реально различимый портрет покупателя, один Сегмент = одно решение о покупке.

**Имя:** портрет покупателя человеческим языком. ✓ «Офис-менеджер 50+», «Владелец премиум-квартиры» / ✗ «seg_b2b», «ЦА_1».

**Что писать:** Описание (человеческий язык, не маркетинговый ICP), Размер (число с источником), Ранние (конкретные группы первых покупателей — не «энтузиасты»). Для B2B опционально: Выручка / Стадия / Платёжеспособность / ЛПР.

**На чём основываться:** отзывы конкурентов в 2GIS/Yelp/Otzovik (демография), Wordstat (объём ниши), интервью с клиентами.

**Антипаттерны:** «целевая аудитория от 18 до 65»; Размер «много»; смешивание B2B и B2C в одном Сегменте.

### Работа

_Файл: `jobs/<имя>.pflow` · keyword: `работа`_

**Зачем:** JTBD — что человек хочет сделать, БЕЗ упоминания продукта. Если в Хочу/Чтобы появилось «приложение» / «сервис» / «фича» — это уже Предложение, не Работа.

**Имя:** формулировка работы глаголом, без продукта. ✓ «Вернуть ковёр в чистое состояние без риска повредить» / ✗ «job_clean», «использовать наш сервис».

**Что писать:** Когда (триггер — что случилось перед тем как «нужно»), Хочу (что сделать), Чтобы (мотивация), Но (главный барьер — продукт-агностично), Тип (функциональный/эмоциональный/социальный), Сегменты[] (кто эту Работу делает).

**На чём основываться:** жалобы и формулировки из отзывов конкурентов, цитаты из интервью.

**Антипаттерны:** «Хочу пользоваться нашим продуктом»; пустое «Но»; абстрактный Триггер «когда нужно».

### Доход

_Файл: `canvases/<имя>-dohod.pflow` · keyword: `доход`_

**Зачем:** модель монетизации Канваса. Один Доход = одна revenue-модель. Если есть подписка И разовые — это два Дохода.

**Имя:** revenue-модель фразой. ✓ «Оплата по м² с надбавкой за срочность» / ✗ «rev1», «доход_основной».

**Что писать:** Модель (подписка/разово/реклама/транзакция/лицензия/freemium/...), Цель (целое число — сколько в одной транзакции/подписке), Валюта (RUB/USD/EUR), Период (если применимо — месяц/квартал/год).

**На чём основываться:** конкурентные тарифы, ценовая стратегия команды.

**Антипаттерны:** Цель = 0 для существующей модели; смесь двух revenue-моделей в одном Доходе.

### Расходы

_Файл: `canvases/<имя>-rashody.pflow` · keyword: `расходы`_

**Зачем:** фиксированные затраты Канваса (run-rate). Переменные расходы (зарплаты за выполнение Услуги) — НЕ сюда.

**Имя:** статья затрат фразой. ✓ «Лизинг забора + ФОТ курьера» / ✗ «costs», «расходы_1».

**Что писать:** Сумма (целое), Валюта, Период (месяц/квартал/год). Тело опционально — категорийные статьи без цифр.

**На чём основываться:** реальный бюджет команды/инструментов.

**Антипаттерны:** смешивание разовых и постоянных трат; пустая Сумма; «разные расходы» вместо разбивки по типам.

### Канал

_Файл: `canvases/<имя>-kanal.pflow` · keyword: `канал`_

**Зачем:** способ привлечения клиентов с unit-economics. Один Канал = один источник трафика.

**Имя:** конкретный источник трафика. ✓ «Органический поиск 'химчистка после ремонта'» / ✗ «seo», «соцсети».

**Что писать:** Тип (входящий/исходящий/вирусный/партнёрский), Стоимость (свободная строка про бюджет), опционально CAC / LTV / ARPU / Конверсия (целые числа — для расчёта payback).

**На чём основываться:** реальные данные из аналитики/CRM; для гипотетических Каналов — пустые цифры, не «50%».

**Антипаттерны:** «соц. сети» как один Канал (FB и YT — разные); LTV/CAC < 3 без обоснующего Сигнала; ARPU=0 для действующего канала.

### Переключение

_Файл: `switches/<имя>.pflow` · keyword: `переключение`_

**Зачем:** Demand-Side Sales 4 силы — описывает миграцию пользователя на наш продукт от того, что было раньше.

**Имя:** миграция «с X на Y». ✓ «С домашней пены на цех с камерой» / ✗ «switch1», «переход_1».

**Что писать:** Работа (ref), Ситуация (опц., связь с GTM-триггером), Толчок (что случилось плохого с прежним решением: Проблема + Момент), Притяжение (что обещает наш: Привлекает + Обещание), Тревога (страхи: Про_новое + Про_процесс), Привычка (что было раньше: Альтернативы + Норма_среды), Хронология (4 этапа от первой мысли до первого опыта).

**На чём основываться:** глубинные интервью с теми, кто РЕАЛЬНО перешёл на нас. Без интервью — не пиши Переключение.

**Антипаттерны:** всё придумано без интервью; Толчок «они хотели лучшего»; Хронология «они увидели → купили» (слишком плоско).

### Связка (пакет)

_Файл: `portfolio/bonds/<имя>.pflow` · keyword: `связка-пакет`_

**Зачем:** портфельная связь — два Канваса продаются вместе как пакет. Усиливает LTV / снижает CAC.

**Имя:** что с чем в пакете. ✓ «Премиум-чистка + годовой офис одним пакетом» / ✗ «bundle1».

**Что писать:** Тип (пакет), База (первый Канвас), Дополнение (второй Канвас), Условие (когда срабатывает), опц. Скидка/бонус.

**На чём основываться:** реальная маркетинговая упаковка, повторяющиеся кейсы продаж.

**Антипаттерны:** Связка между Канвасами разных Юнитов (это уже не один портфель); пакет без Условия.

### Связка (апселл)

_Файл: `portfolio/bonds/<имя>.pflow` · keyword: `связка-апселл`_

**Зачем:** клиент Канваса A переходит в Канвас B как апселл. Усиление LTV через cross-sell.

**Имя:** что во что апселлится. ✓ «Офисная чистка как апселл к B2C» / ✗ «upsell1».

**Что писать:** Тип (апселл), База (откуда), Дополнение (куда), Условие (триггер апселла), Скидка/механика.

**На чём основываться:** реальная конверсия из существующих апселл-кампаний.

**Антипаттерны:** Апселл без Условия; гипотетический процент конверсии без измерения.

### Петля

_Файл: `portfolio/loops/<имя>.pflow` · keyword: `петля`_

**Зачем:** возврат клиента из Канваса B обратно в Канвас A (или вторичная покупка). Снижает CAC за счёт повторных продаж.

**Имя:** механика возврата фразой. ✓ «Возврат через офис-партнёра» / ✗ «loop1».

**Что писать:** Из (Канвас), В (Канвас), Триггер (что заставляет вернуться), Канал (опц. — какой Канал того Канваса служит точкой возврата), Усиление (какая механика поддерживает Петлю).

**На чём основываться:** воронка возврата — какой % через какой канал возвращается.

**Антипаттерны:** «они вернутся» без механизма; Петля без Триггера; недостижимый Канал.

### Партнёр

_Файл: `partners/<имя>.pflow` · keyword: `партнёр`_

**Зачем:** внешняя сила, которая влияет на канал доступа / стоимость / комплементарность. BMC-блок Партнёров.

**Имя:** имя/название партнёра (как в реальности). ✓ «БизнесЦентр Невский», «ClickHelp (Answer Genius)» / ✗ «partner_a», «партнёр_1».

**Что писать:** Роль (стратегический/канал_доступа/комиссионный/...), Доступ_к[] (Сегменты, к которым партнёр даёт доступ), Тип_договорённости (партнёрский/совместный_продукт/...), Статус (действующий/в_переговорах/...), Описание (что именно за партнёр).

**На чём основываться:** подписанные соглашения или реальные отношения с историей.

**Антипаттерны:** «потенциальный партнёр» со Статус: действующий; Партнёр без Доступ_к (тогда непонятно, как именно влияет на Канвас).

### Ресурс

_Файл: `resources/<имя>.pflow` · keyword: `ресурс`_

**Зачем:** ключевой актив BMC — на чём держится продукт. Может быть интеллектуальный / технический / человеческий / социальный / финансовый.

**Имя:** актив конкретной фразой. ✓ «Команда мастеров с опытом 5+ лет», «Цех с камерой видеонаблюдения» / ✗ «team», «ресурс_2».

**Что писать:** Тип, Описание (что именно за актив, как добывается и поддерживается).

**На чём основываться:** реальный инвентарь команды (а не «было бы хорошо иметь»).

**Антипаттерны:** «команда» как Ресурс (слишком общо — лучше «команда из N мастеров с навыком X»); «доступ к интернету» как Ресурс.

### Активность

_Файл: `activities/<имя>.pflow` · keyword: `активность`_

**Зачем:** регулярный процесс команды — макропроцесс BMC. Что мы делаем еженедельно/ежемесячно/ежеквартально для поддержания Ресурсов.

**Имя:** процесс глаголом/отглагольно. ✓ «Обзвон B2B-базы перед сезоном», «SEO-публикации в блоге» / ✗ «activity1», «процесс_3».

**Что писать:** Регулярность (еженедельная/ежемесячная/квартальная/постоянная), Описание (что именно делается), Поддерживает[] (Ресурсы, которые активность наращивает).

**На чём основываться:** реальные планёрки и регламенты команды.

**Антипаттерны:** «мы будем делать X» как существующая Активность; Активность без Поддерживает (зачем тогда регулярность?).

### Компонент

_Файл: `components/<имя>.pflow` · keyword: `компонент`_

**Зачем:** модуль операционного слоя. Из чего собираются svcflow:Услуги (через `Услуга.Состав:`). Семейство+Уровень группируют варианты разной зрелости одного типа.

**Имя:** модуль конкретно. ✓ «ЭДО-интеграция Контур.Диадок», «Видео-запись процесса» / ✗ «module1», «компонент_crm».

**Что писать:** Тип (процесс/артефакт/продукт/интеграция/агент/библиотека), Семейство, Уровень, Состояние (действующий/в_работе/устаревший), Описание, Зависит_от[] (другие Компоненты).

**На чём основываться:** реальный инвентарь tooling/процессов команды.

**Антипаттерны:** один Компонент = вся CRM (слишком крупно — разбей на под-Компоненты); Компонент без ссылки из какой-либо Услуги.

### Альтернатива

_Файл: `alternatives/<имя>.pflow` · keyword: `альтернатива`_

**Зачем:** что клиент использует ВМЕСТО нашего продукта. Не путать с Развилкой — Альтернатива про рынок, Развилка про наш внутренний выбор.

**Имя:** что рынок делает вместо нас — фразой действия. ✓ «Купить новый ковёр», «Чистить самому пеной» / ✗ «купить_новый_ковёр», «alt_buy».

**Что писать:** Тип (заместитель/самодельное/...), Описание.

**На чём основываться:** ответы в интервью «что вы делали до этого», конкурентный анализ.

**Антипаттерны:** смешивание Альтернативы (рынок) с Вариантом Развилки (внутренний выбор); Альтернатива без описания «как это решает Работу».

### Предпосылка

_Файл: `premises/<имя>.pflow` · keyword: `предпосылка`_

**Зачем:** scope-ограничение / founder's bet / зафиксированный пивот. Защищает узлы от попадания в `state.unfounded` (но только Премиссы с Пересмотр: твёрдая).

**Имя:** утверждение-ставка/ограничение фразой. ✓ «Работаем только в премиум-сегменте», «Не восстанавливаем б/у ковры» / ✗ «Только_премиум_сегмент», «premise1».

**Что писать:** Тип (ставка/ограничение/компетенция), Причина (почему так), Пересмотр (твёрдая/мягкая/на_срок), Дата (для на_срок — обязательно), Источник (founder / team / external), Влияет_на[] (Refable-ссылки на узлы, которые Премисса защищает).

**На чём основываться:** явные осознанные решения фаундера/команды. Не «мы предполагаем» — а «мы выбрали».

**Антипаттерны:** пустое Влияет_на (тогда Премисса никого не защищает); мягкая Премисса без plan для пересмотра; ставка с Пересмотр: твёрдая без обоснования в Причине.

### Развилка

_Файл: `decisions/<имя>.pflow` · keyword: `развилка`_

**Зачем:** точка стратегического выбора с историей. Что рассматривали внутри команды, что выбрали, почему, когда пересмотреть. Через 3-6 месяцев напомнит, почему мы здесь.

**Имя:** принятое решение + (дата) в скобках. ✓ «Ставка на видеонаблюдение в цехе (2024-12)», «Модель ценообразования B2B (2025-04)» / ✗ «Подход_видео_2024-12», «decision1».

**Что писать:** Вопрос (что решали), Варианты[] (что рассматривали), Выбрано (один вариант), Причина (почему именно этот), Пересмотреть_если (триггер re-eval), Статус (открыта/решена), Дата, Влияет_на[] (Refable-ссылки).

**На чём основываться:** реальные обсуждения внутри команды с конкретной датой.

**Антипаттерны:** Развилка без Причины (выбор без обоснования); без Пересмотреть_если (значит навсегда — редко правда); смешивание с Альтернативой.

### Ситуация

_Файл: `situations/<имя>.pflow` · keyword: `ситуация`_

**Зачем:** GTM-атом — Триггер + ЛПР + Работа. Когда конкретно и у кого боль активна настолько, чтобы перейти к покупке. Один лендинг / outbound-кампания = одна Ситуация.

**Имя:** триггер-момент рынка (что случилось, почему «надо сейчас») — НЕ так же, как svcflow:Контекст, который её реализует. ✓ «Ремонт квартиры закончен — грязные ковры до приезда семьи» / ✗ «После_ремонта_квартиры» (совпадёт с Контекстом).

**Что писать:** Триггер (конкретный момент жизни/работы), ЛПР[] (Сегменты, кто принимает решение), Работа (ref), Срочность (низкая/средняя/высокая/критическая), Описание (что вокруг происходит), Неясно (что в этой Ситуации не подтверждено).

**На чём основываться:** интервью с реальными покупателями — какой момент привёл к решению.

**Антипаттерны:** Ситуация без Триггера («иногда нужно...»); имя как у одноимённого Контекста (не видно слоя); Срочность «средняя» по умолчанию без обоснования; ЛПР пустой или «все».

### Результат

_Файл: `outcomes/<имя>.pflow` · keyword: `результат`_

**Зачем:** ODI Outcome — гипотеза о метрике, которую мы хотим сдвинуть. На неё ссылаются VPC.ERRC.Поднять/Создать (наши Blue Ocean ставки) и svcflow:Обещание.Закрывает.

**Имя:** метрика/направление фразой. ✓ «Прозрачность процесса для клиента», «Цветостойкость проверена до приёмки» / ✗ «Прозрачность_процесса», «outcome1».

**Что писать:** Направление (увеличить/уменьшить/избежать), Что (формулировка метрики — что именно измеряем), Цель (число / диапазон / частота), опц. Работа (привязка к JTBD).

**На чём основываться:** продуктовая стратегия, Blue Ocean анализ, OKR процессы.

**Антипаттерны:** Результат без Цели (тогда не метрика, а пожелание); «увеличить вовлечённость» без определения как измеряем; Цель «> 0».

### Сигнал

_Файл: `signals/<имя>.pflow` · keyword: `сигнал`_

**Зачем:** наблюдение из реального мира, обосновывающее или опровергающее декларацию в модели. Цель — путь-ссылка `Тип."имя"/...` в Подтверждает / Опровергает / Связан.

**Имя:** сам тезис наблюдения. ✓ «90% B2C-клиентов смотрят камеру хотя бы раз», «ремонт — главный триггер первого обращения» / ✗ «signal1», «сигнал_рынок».

**Что писать:** Наблюдение (конкретный факт без интерпретации), Источник (URL / файл / транскрипт интервью), Категория (кабинет/эксперт/пользователь/продажа/метрика), Дата (для эксперт+ обязательна), Подтверждает / Опровергает / Связан [пути].

**На чём основываться:** реальные данные с реальным источником. Никаких «многие говорят».

**Инбокс (черновик):** на быстром кабинетном ресёрче можно завести Сигнал без цели — оставь Подтверждает/Опровергает/Связан пустыми, добавь `Касается:` со свободным текстом для контекста, клади в `signals/inbox.pflow`; цель проставишь при разборе.

**Антипаттерны:** Сигнал без Источника; обобщающее «многие/часто/обычно» в Наблюдении; Категория случайная (например, кабинетная без ссылки на открытый источник); инбокс-черновики, висящие неразобранными неделями.

## svcflow — операционный слой

### Услуга

_Файл: `services/<имя>.sflow` · keyword: `услуга`_

**Зачем:** операционный продукт. Один заказ клиента = одна Услуга. Реализует одно или несколько pflow:Предложений — это связь стратегии и операций.

**Имя:** оффер фразой, как клиент его называет. ✓ «Экспресс-чистка за 24 часа», «Годовое обслуживание ковров» / ✗ «экспресс_чистка_24ч», «service1».

**Что писать:** Статус (идея/в_работе/действующая), Реализует[] (pflow:Предложения), Работа (ref pflow), Сегменты[], Персоны[], Контексты[], Результат, Обещания[], Опоры[], Срок, Цена (целое), Период (месяц/разово/...), Валюта, Состав[] (Компоненты).

**На чём основываться:** upstream Предложение (pflow Стратегия), реальная capacity (Опоры, Компоненты).

**Антипаттерны:** Услуга без Реализует (свободное плавание — нарушает связь стратегии и операций); Цена 0 для действующей Услуги; Сегменты не совпадают с pflow:Сегментами реализуемого Предложения.

### Обещание

_Файл: `promises/<имя>.sflow` · keyword: `обещание`_

**Зачем:** то, что клиент получает на руки. Привязка к pflow:Результату через `Закрывает:` делает Обещание измеримым через ODI-метрику.

**Имя:** что клиент получит — глагол + результат, голосом клиента. ✓ «Вернём через сутки», «Не повредим ворс и цвет» / ✗ «promise1», «обещание_качество».

**Что писать:** Формулировка (что именно получит — глагол + результат), Кому[] (Персоны), Закрывает[] (pflow:Результаты — какую метрику сдвигает), Инвариант[] (pflow:Ресурсы — на каких активах держится).

**На чём основываться:** голос клиента + product strategy (ODI Outcomes).

**Антипаттерны:** «лучший сервис» как Формулировка; Обещание без Закрывает (тогда оно не привязано к метрике); пустое Кому.

### Персона

_Файл: `personas/<имя>.sflow` · keyword: `персона`_

**Зачем:** конкретный покупатель внутри pflow:Сегмента. Один Сегмент может иметь несколько Персон с разными ролями / контекстами / триггерами.

**Имя:** «Имя (роль/контекст)» — человек, а не код. ✓ «Марина (владелец премиум-квартиры)», «Сергей (офис-менеджер 50+)» / ✗ «Марина_квартира», «persona1».

**Что писать:** Сегмент (ref pflow), Описание (что отличает эту Персону в Сегменте — роль, ситуация, тип решения).

**На чём основываться:** интервью с конкретными типами клиентов внутри Сегмента.

**Антипаттерны:** Персона == Сегмент (тогда лишняя сущность — просто наполни Сегмент.Описание); Описание «среднестатистический клиент».

### Контекст

_Файл: `contexts/<имя>.sflow` · keyword: `контекст`_

**Зачем:** связка Работа × Персона × Триггер — в каких ситуациях боль активна. Лежит между JTBD-абстракцией и конкретной транзакцией.

**Имя:** «<Персона>: <ситуация обслуживания>» — операционный слой, привязка к персоне. НЕ называй так же, как pflow:Ситуацию, которую реализуешь (поле `Ситуация:`). ✓ «Марина: ковёр после ремонта квартиры» / ✗ «после ремонта квартиры» (совпадёт с Ситуацией → не видно слоя).

**Что писать:** Работа (ref pflow), Персоны[], Ситуация (ref на pflow:Ситуацию), Эмоция (что чувствует клиент), Триггер (момент решения), Что_важно[] / Что_не_важно[], Обещания[] с пометкой `-> ключевое`, Каналы[] (pflow:Каналы из Канваса), Альтернативы[] (pflow:Альтернативы), Приоритет (низкий/.../критический — НАШ выбор инвестиций), Сила (низкая/средняя/высокая — ФАКТ рынка, реальность спроса).

**На чём основываться:** интервью + воронка реального спроса. Приоритет и Сила — независимые шкалы.

**Антипаттерны:** имя как у реализуемой Ситуации (не видно слоя); Приоритет=критический + Сила=низкая (запах: инвестируем в несуществующий рынок); Контекст без Триггера; смешивание Эмоции и Триггера.

### Сценарий

_Файл: `scenarios/<имя>.sflow` · keyword: `сценарий`_

**Зачем:** «как Услуга работает» в Gherkin-формате. Услуга × Персона × Контекст → шаги Дано/Когда/Тогда.

**Имя:** история клиента действием. ✓ «Марина сдаёт ковёр после ремонта», «Сергей заказывает годовую чистку офиса» / ✗ «ковёр_марины_после_ремонта», «scenario1».

**Что писать:** Услуга / Персона / Контекст (3 ref), Показывает[] (Обещания, которые сценарий демонстрирует), Статус (черновик/готов), Дано[] (стартовая ситуация), Когда[] (шаги пользователя), Тогда[] (результаты), Опоры[].

**На чём основываться:** реальный flow из user testing'а или production.

**Антипаттерны:** Сценарий без Опор (не понимаем на чём держится); абстрактные Тогда «клиент доволен»; смешивание шагов разных Персон.

### Опора

_Файл: `pillars/<имя>.sflow` · keyword: `опора`_

**Зачем:** на чём держится Обещание. Актив (физический/цифровой), процесс (повторяемая работа), методология (know-how), социальная связь (партнёр/комьюнити).

**Имя:** «Нужно X, чтобы Y» — что требуется и зачем (Опора = требуемая способность сервиса). ✓ «Нужна своя машина для забора ковров», «Нужна камера в цехе для трансляции чистки» / ✗ «своя_машина_забора», «pillar1».

**Что писать:** Тип (актив/процесс/методология/социальная), Состояние (есть/в_работе/нет), Описание, Стоимость (вложения / поддержка), Обеспечивает[] (pflow:Ресурс — какому активу служит).

**На чём основываться:** реальный аудит «что у нас есть и что нужно».

**Антипаттерны:** Опора «есть» когда на самом деле «в_работе»; Опора без Обеспечивает; смешивание двух типов в одной Опоре.

### Апгрейд

_Файл: `upgrades/<имя>.sflow` · keyword: `апгрейд`_

**Зачем:** переход клиента между Услугами. Воронка апселла, downgrade, или цикла повторных покупок.

**Имя:** переход «X → Y». ✓ «стандарт → экспресс 24ч», «стандарт → годовое обслуживание» / ✗ «upgrade1», «апгрейд_1».

**Что писать:** Из (Услуга-источник), В (Услуга-цель), Условие (триггер перехода — что побуждает), Конверсия (целое 0-100, опц.).

**На чём основываться:** реальная воронка из CRM/аналитики.

**Антипаттерны:** Апгрейд без Условия; Конверсия 50% гипотетически без измерения; Апгрейд между Услугами разных Продуктов без обоснования.

### Зависимость

_Файл: `dependencies/<имя>.sflow` · keyword: `зависимость`_

**Зачем:** правило: что нельзя купить без чего, или что несовместимо. Бизнес-правила оформления услуг.

**Имя:** правило фразой. ✓ «Экспресс требует pre-теста цветостойкости» / ✗ «dep1», «зависимость_1».

**Что писать:** Услуга (владелец правила), Требует[] (Услуги-пререквизиты), Тип (пререкизит/совместимость/исключение), Обязательно (true/false).

**На чём основываться:** правила биллинга / договоров.

**Антипаттерны:** Зависимость без Услуги-владельца; Обязательно=true когда на самом деле опционально (это раздувает воронку отказов).

### Продукт

_Файл: `products/<имя>.sflow` · keyword: `продукт`_

**Зачем:** упаковка svcflow:Услуг под одним брендом. Аналог pflow:Канваса на операционном слое — каждому Канвасу соответствует один Продукт.

**Имя:** линейка/бренд. ✓ «Премиум B2C-линейка» / ✗ «product1», «продукт_основной».

**Что писать:** Канвас (ref pflow), Основная (одна ключевая Услуга — флагман), Уровни[] (Услуги-tier'ы, например basic/pro/enterprise), Опции[] (add-on Услуги, отдельная покупка).

**На чём основываться:** реальная маркетинговая упаковка (страница тарифов сайта).

**Антипаттерны:** Продукт без Основной Услуги; Опции дублируют Уровни (тогда это один уровень с включёнными опциями); Канвас-Продукт-many-to-many.

### Трек

_Файл: `tracks/<имя>.sflow` · keyword: `трек`_

**Зачем:** маршрут pflow:Сегмента через Продукт. Какой путь конкретный сегмент проходит из Услуги в Услугу.

**Имя:** маршрут сегмента фразой. ✓ «B2C онбординг», «B2B годовой контракт» / ✗ «track1», «трек_1».

**Что писать:** Продукт (ref), Сегмент (ref pflow), Этапы[] (Услуги в ПОРЯДКЕ прохождения), Апгрейды[] (УЖЕ существующие Апгрейды между соседними Этапами — НЕ создавай новые inline).

**На чём основываться:** реальный customer journey конкретного сегмента.

**Антипаттерны:** Этапы хаотичные не в порядке клиентского пути; ссылка на несуществующие Апгрейды; Трек разных Продуктов.

### Портфель

_Файл: `portfolios/<имя>.sflow` · keyword: `портфель`_

**Зачем:** иерархия Продуктов и Треков одной командной единицы. Аналог pflow:Юнита на операционном слое.

**Имя:** командная единица/бренд (обычно как Юнит). ✓ «Премиум химчистка» / ✗ «portfolio1», «портфель_1».

**Что писать:** Юнит (ref pflow), Продукты[], Треки[].

**На чём основываться:** реальная орг-структура команды.

**Антипаттерны:** Портфель с Продуктами разных Юнитов (нарушает one-team — one-portfolio); пустой Портфель без Продуктов и Треков.
