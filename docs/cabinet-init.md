# Кабинетная инициализация воркспейса

Воркфлоу для агента: первоначальное заполнение pflow-воркспейса на основе открытых данных.
Человек принимает решения в Развилках и в моменте пивота — всё остальное делает агент.

**Входные данные:** URL сайта референса.
**Выход:** pflow-воркспейс с полным набором сущностей под фокусную Ситуацию: Юнит, лестница
Канвасов с VPC и ERRC, Результаты, Переключение с 4 силами, типизированная экономика
(Каналы с CAC/LTV, Доходы, Расходы), Ресурсы/Активности/Партнёры/Компоненты, Связки/Петли
где есть синергии, Сигналы под каждое утверждение, закрытые Развилки, Предпосылки
(включая пивоты) с `Влияет_на:`, открытые вопросы и план выхода в поле.

**Вне scope:** svcflow (Услуга / Продукт / Трек / Портфель / Обещание / Опора / Сценарий).
Для них — отдельная методика «Операционализация».

---

## Принципы

**Сигнал на каждый факт.** Любое наблюдение из открытых источников — это `Сигнал` с URL
и датой. Три предиката: `Подтверждает:` / `Опровергает:` / `Связан:` (нейтральный
контекст). Без источника — не пишем, а помечаем `Неясно:` в ближайшей Ситуации.

**Развилка при двух+ вариантах внутри текущего контура.** Если все варианты совместимы
с уже собранным (это внутрикомандный выбор реализации) — агент создаёт `Развилка`
(Статус: открыта) и останавливается для решения человека. Не накапливает, не выбирает
сам. У Развилки **обязательно** заполняется `Влияет_на:` — те сущности, чьё содержание
зависит от выбора.

**Пивот — не Развилка, а Предпосылка.** Если хотя бы один вариант обесценивает уже
собранное — это пивот. Чеклист обесценивания: меняется тип клиента (B2B/B2C/гос),
Сегмент, география, продуктовая категория, ценовой класс, канал привлечения, формат
работы (продукт/услуга/маркетплейс). Агент обязан назвать вариант пивотом **до** выбора:
«Этот вариант — пивот. Данные про X становятся неприменимы, работа возвращается на шаг N.»
После решения человека — новый фокус закрепляется как `Предпосылка` (Тип: ставка,
Пересмотр: твёрдая) с заполненным `Влияет_на:`, и одним атомарным commit'ом удаляются
обесценившиеся сущности. Причина пивота — в commit message:

```
Пивот: <откуда> → <куда>

Основание: <причина из слов человека>
Удалено: <перечень сущностей>
Закреплено: Предпосылка "<имя>"
```

Для частичного пивота — два commit'а: сначала Предпосылка + список «под удаление» с
подтверждением человека, потом `git rm`. Воркспейс отражает текущую гипотезу, не музей
отвергнутых; история — в `git log`.

**`Влияет_на:` — обязательное поле у Предпосылок и Развилок.** Без него твёрдая Премисса
не защищает новые сущности от попадания в `state.unfounded`, а Развилка не показывает
свою область влияния. Заполнять сразу при создании.

**Человек только объясняет природу решения.** Ответ человека → `Развилка.Причина:`
(или `Предпосылка.Причина:` при пивоте) дословно. Агент сам пишет `Выбрано:`, закрывает
`Статус: решена` и продолжает.

**Пустоту не достраиваем.** Если данных нет — поле остаётся пустым или помечается
`Неясно:`. Реконструированная модель хуже честной дыры: дыру можно проверить.

**Блочное дробление.** Конкурентный обход BMC идёт по одному блоку за раз. Длинный
запрос — пролистанный артефакт; блок вынуждает остановиться и прочитать.

## Шаг 0 — Разведка референса

**Кто работает:** агент, автономно.
**Источники:** только сайт референса.

1. Читает сайт: продукты, позиционирование, заявленная аудитория, цены если видны.
2. Создаёт черновой `Юнит` с именем направления (не компании): «SEO-аудиты для ecom»,
   «Подписка на дизайн».
3. На каждый продукт с сайта — черновой `Канвас` + одна или несколько `VPC` под каждый
   Сегмент: УТП из заголовка → `VPC.УТП:`, Сегмент → `VPC.Сегмент:`, Предложение → `Предложение:`
   внутри VPC. Канвас связывается с VPC через `Канвас.VPC:`.
4. Черновые `Сегмент` и `Работа` — из формулировок сайта. В `Работа` идёт то, как клиент
   формулирует задачу, а не как агентство её описывает.
5. На каждый факт — `Сигнал` (Категория: кабинет, Источник: URL, Дата: сегодня,
   `Подтверждает:` указывает на конкретную сущность).
6. Находит 4–5 прямых конкурентов (раздел «Нас сравнивают с», мета-теги, видимые ссылки).
   Фиксирует URLs — они нужны на шаге 1.

**Человек:** не вмешивается.

**Переход к шагу 1:** черновики созданы, конкуренты найдены.

## Шаг 1 — Конкурентный обход BMC (9 блоков)

**Кто работает:** агент блок за блоком; человек один раз в конце.
**Источники:** сайты 4–5 конкурентов + сайт референса.

**Что ищем в каждом блоке:** что совпадает у всех (рыночные нормы) — и что различается
или пусто (кандидаты в нишу).

| № | Блок BMC | Что создаём в воркспейсе |
|---|---|---|
| 1 | Сегменты | Уточнения к черновым `Сегмент` (как кто называет, формулировки клиента vs агентства). Дополнительные `Сигнал`. |
| 2 | Ценностное предложение | `Сигнал` с УТП дословно. Повторения у всех → нормы рынка → Предпосылки в конце шага. |
| 3 | Каналы | На каждый канал — `Канал` с `Тип:` (входящий / исходящий / вирусный / партнёрский). Метрики (CAC/LTV/ARPU/Конверсия) — в Шаге 4, под наши гипотезы. |
| 4 | Отношения с клиентами | Поле `Канвас.Отношения:` (Воронка / Формат / Долгосрочность) — на уровне рыночной нормы. |
| 5 | Потоки доходов | `Сигнал` с ценовыми диапазонами конкурентов. Типизированный `Доход` (Сумма / Валюта / Период) — в Шаге 4. **Строгая планка**: только явные данные. |
| 6 | Ключевые ресурсы | На каждый декларируемый — `Ресурс` (`Тип:` интеллектуальный / технический / человеческий / социальный / финансовый). |
| 7 | Ключевые активности | На каждую — `Активность` (`Регулярность:` постоянная / еженедельная / ежемесячная / квартальная / годовая). |
| 8 | Партнёры | На каждого — `Партнёр` (`Роль:` стратегический / канал_доступа / методический / технический; `Статус:` гипотеза / в_переговорах / действующий). |
| 9 | Структура затрат | `Сигнал` по публичным данным (вакансии, описания команды). **Строгая планка**: не реконструировать. |

После каждого блока — Сигналы.

**После всех блоков агент:**
- Для каждой рыночной нормы («все делают X, иначе не работает») создаёт `Предпосылка`
  (Тип: ограничение, Пересмотр: твёрдая, `Влияет_на:` указывает на затронутые сущности).
- Для каждого зазора («никто не закрывает Y у аудитории Z») — `Сигнал`: сырой кандидат
  в нишу, ещё не сущность.

**Человек:** читает Предпосылки, корректирует формулировки и `Влияет_на:`, подтверждает
или снимает.

**Переход к шагу 2:** Предпосылки зафиксированы.

## Шаг 2 — Голос клиента: Ситуации + Переключение

**Кто работает:** агент; человек — в Развилке / пивоте.
**Источники:** отзывы на конкурентов (отзовики, vc.ru, Telegram-каналы), задания на
биржах (как клиент сам формулирует задачу), форумы предпринимателей, комментарии.

**Что ищет агент:**
- Как клиент описывает свою ситуацию **своими словами**.
- Что не закрывают текущие игроки: жалобы, формулировки «хотел бы, но не нашёл».
- Разрыв между сайтами агентств и отзывами клиентов.

**2.1 — Портреты → Ситуации.**
1. 3–5 портретов: Кто + В какой ситуации + Триггер + Ограничение + Как сам формулирует
   результат.
2. На каждый портрет — `Ситуация` (Описание / Триггер / ЛПР / Работа / Срочность).
   Неподтверждённые части — в `Неясно:`.
3. `Сигнал` (Категория: пользователь) с дословными цитатами и ссылками.
4. Каждый зазор из шага 1 сверяется с живыми высказываниями: подтверждается или
   попадает в `Сигнал.Опровергает`.

**2.2 — Переключение (4 силы JTBD).**
Для каждой Ситуации, где клиент мигрирует с предыдущего решения, — `Переключение` с
обязательной ссылкой `Ситуация:`:
- **Push** — что выталкивает из текущего: `Проблема:` + `Момент:`.
- **Pull** — что притягивает к новому: `Привлекает:` + `Обещание:`.
- **Anxiety** — что мешает: `Про_новое:` + `Про_процесс:`.
- **Habit** — что удерживает: `Альтернативы:` + `Норма_среды:`.
- **Timeline** — 5 точек: `Первая_мысль:` → `Пассивный_поиск:` → `Активный_поиск:` →
  `Решение:` → `Первый_опыт:`.

Каждая заполненная сила подкреплена `Сигнал` (Категория: пользователь). Если данных по
силе нет — пропускаем поле (пустоту не достраиваем) и помечаем в `Неясно:` соответствующей
Ситуации, что именно нужно проверить.

**2.3 — Развилка фокуса или пивот.**
Если агент видит 2+ жизнеспособных Ситуаций для фокуса — применяет чеклист пивота.

- **Все кандидаты в текущем контуре** → `Развилка "Выбор_фокусной_ситуации"`
  (Статус: открыта, `Вопрос:`, `Варианты:` с одной строкой «почему кандидат»,
  `Влияет_на:` на Канвасы / VPC / Работы фокуса). Человек называет Ситуацию, агент
  пишет `Причина:`, ставит `Статус: решена` и `Срочность:` в выбранной Ситуации.
- **Хотя бы один кандидат — пивот** → агент явно называет пивотом, описывает откат.
  При выборе пивот-варианта — `Предпосылка` (Тип: ставка, Пересмотр: твёрдая,
  `Влияет_на:`), commit с удалением, возврат на шаг 0 с новым референсом если требуется.

**Переход к шагу 3:** фокусная Ситуация и её Переключение зафиксированы.

## Шаг 3 — Стратегия: Результаты + ERRC + VPC

**Кто работает:** агент; человек — в Развилках.
**Источники:** данные шагов 0–2 + сайты конкурентов под фокусную Ситуацию.

**3.1 — Конкурентное покрытие фокусной Ситуации.**
По каждому конкуренту — одна строка: какой продукт под эту Ситуацию, что в нём слабо.
Каждое наблюдение → `Сигнал`.

**3.2 — Результаты (ODI Outcomes).**
Какие метрики клиента мы сдвигаем — наши ставки. 3–6 Результатов под фокусную Ситуацию.
Каждый `Результат`:
- `Работа:` (cross-ref на pflow:Работа — какой Job закрывает).
- `Направление:` (уменьшить / увеличить / избежать).
- `Что:` — метрика словами клиента (не нашими).
- `Цель:` — текстовая формулировка планки (например, «< 30 минут», «> 80%»).

Каждый Результат подкреплён `Сигнал`, подтверждающим что клиенту это действительно важно
(из отзывов / форумов / задач на биржах).

**3.3 — VPC и ERRC под фокусный Сегмент.**
`VPC` с полями:
- `Сегмент:`, `Работы:`, `УТП:`.
- `Альтернативы:` — что клиент использует вместо нас. Каждая — отдельная сущность
  `Альтернатива` (`Тип:` замещение / самодельное / отказ / альтернативный_продукт;
  `Описание:`). Не путать с Развилкой: Альтернатива — что **рынок** делает;
  Развилка — что **мы внутри команды** рассматривали.
- **ERRC** (Blue Ocean) внутри VPC:
  - `Убрать:` — атрибуты индустрии, которые мы отбрасываем (свободные строки, опираются
    на нормы из шага 1).
  - `Снизить:` — атрибуты, которые ослабляем относительно конкурентов.
  - `Поднять:` — наши `Результат`'ы, которые усиливаем выше индустрии (cross-ref).
  - `Создать:` — `Результат`'ы, которые вводим впервые в категории (cross-ref).
- `Предложение:` — список Предложений внутри VPC. У каждого:
  - `Решает:` (cross-ref на Работу).
  - `Подход:` (как именно решаем).
  - `Статус:` (гипотеза / в_работе / работает).
  - `Покрытие:` (полное / частичное).

Для каждого Предложения с выбором подхода — `Развилка:` с `Влияет_на:` на затронутые
сущности. Если возникает вариант, обесценивающий ранее собранное — пивот по правилам
Принципов.

**Переход к шагу 4:** VPC и Результаты зафиксированы.

## Шаг 4 — Лестница: 3 Канваса + операционализация

**Кто работает:** агент; человек — в Развилках.

Все ступени строятся под одну фокусную Ситуацию. Если ступень не применима на первой
итерации (например, нет смысла в «развитии») — помечаем `Неясно:` в Юните и пропускаем.
Не достраиваем пустоту.

**4.1 — Лестница (3 Канваса).**

| Ступень | Что | Критерий |
|---|---|---|
| Трипвайер | Первая небольшая работа (аудит, диагностика, пилот) | Даёт пользу сам по себе, без основной услуги |
| Основа | Главная работа — основной источник выручки | Закрывает центральный Job из фокусной Ситуации |
| Развитие | Что покупается после основы | Новая задача в той же ситуации или следующая ситуация того же клиента |

Каждая ступень — отдельный `Канвас` с:
- `Канвас.VPC:` → VPC из Шага 3 (могут быть разные VPC для разных ступеней или одна
  общая под фокусный Сегмент).
- `Канвас.Ситуации:` ← фокусная Ситуация + смежные если применимо.
- `Канвас.Преимущество:` (`UnfairAdvantage`) — defensible moat: что у нас есть, чего
  конкурент не воспроизведёт за месяц. Опционально для трипвайера, обязательно для
  основы.

**4.2 — Каналы с метриками.**
Для каждой ступени — `Канал` внутри Канваса. Если канал уже создан в Шаге 1 как рыночное
наблюдение — Канвас ссылается на него; метрики ставятся под наш случай.
- `Тип:`, `Стоимость:` (свободный текст: «120 тыс RUB/мес ФОТ»), `CAC:` (целое),
  `LTV:` (целое), `ARPU:` (целое), `Конверсия:` (число или диапазон).
- Если метрики гипотетические — `Сигнал.Связан:` со ссылкой на источник ориентира
  (отраслевые отчёты, кейсы) + `Неясно:` в Канвасе про точную ставку.

**4.3 — Деньги: Доходы и Расходы.**
- `Доход` на Канвасе: `Модель:` (подписка / разово / freemium / реклама /
  транзакция / лицензия), `Цель:` (целое), `Валюта:`, `Период:` (default = месяц).
- `Расходы:` — `Сумма:`, `Валюта:`, `Период:`.
- Метрики Юнита: Выручка / Расходы / AOV / Клиенты / LTV — агрегаты по портфелю.
- Валюта согласована на уровне Юнита (`Юнит.Валюта:`).

**4.4 — Инфра: Ресурсы / Активности / Партнёры / Компоненты.**
Привязываем к Канвасам через cross-refs:
- `Канвас.Ресурсы:` → `Ресурс`'ы — наши, а не конкурентов: что у нас есть или нужно
  получить.
- `Канвас.Активности:` → `Активность`'и — что мы регулярно делаем.
- `Канвас.Партнёры:` → `Партнёр`'ы — с кем сотрудничаем.
- `Компонент` — если продукт собирается из модулей: `Тип:` (процесс / артефакт /
  продукт / интеграция / агент / библиотека), `Состояние:` (идея / в_разработке /
  действующий / устаревший), `Семейство:`, `Уровень:`, `Зависит_от:`.

**4.5 — Связки / Петли (опционально).**
Если между ступенями есть синергии:
- `Связка` — как один продукт усиливает другой: `Тип:`, `Участники:`, `База:`,
  `Дополнение:`, `Условие:`.
- `Петля` — как повторное использование создаёт прирост: `Из:`, `В:`, `Триггер:`,
  `Канал:`, `Усиление:`.

Если синергий нет — пропустить, не выдумывать.

**Развилки по ходу.** Любой выбор подхода (формат трипвайера, модель монетизации,
канал) → `Развилка` с `Влияет_на:`. Если вариант обесценивает собранное → пивот.

**Переход к шагу 5:** ступени описаны, экономика заполнена, активных Развилок нет.

## Шаг 5 — Кабинетная верификация: Сигналы и противоречия

**Кто работает:** агент, автономно.

Финальная кабинетная активность. Цель — не подтвердить гипотезы лестницы, а собрать
максимум Сигналов «за» и «против» по каждой и выявить противоречия. Симуляция клиента
не проводится: симуляция на собственных кабинетных данных — эхо-камера.

1. **Зафиксировать гипотезы лестницы** — формат и ценность трипвайера, основа закрытия
   Работы, аудитория и путь к покупке, экономические параметры (CAC / LTV / Конверсия).
2. **Целевой проход по открытым источникам по каждой гипотезе** — дополнительный поиск
   в отзывах, форумах, статьях, отчётах, постах в профессиональных сообществах. Каждый
   найденный факт → `Сигнал` с `Подтверждает:` / `Опровергает:` / `Связан:` на
   конкретную цель (Предложение, Работу, Результат, экономический параметр).
3. **Противоречия вычисляются структурно** — пара `Сигнал.Подтверждает [X]` +
   `Сигнал.Опровергает [X]` на одну цель. Новой сущности не вводим: всё необходимое
   уже есть в индексе Сигналов.

**Граница кабинетной фазы.** Дальнейшие способы проверки (арбитраж эксперта, интервью
с клиентом, тест-продажа) — за пределами «Кабинетной инициализации». Их выбор и
подготовка — артефакт Шага 6.

**Переход к шагу 6:** Сигналы по гипотезам собраны, противоречия квалифицированы.

---

## Шаг 6 — Финализация

**Кто работает:** агент, автономно.

1. **Юнит** — проставляет `Ситуации:`, `Канвасы:`, `Сегменты:`, `Переключения:`,
   `Связки:` / `Петли:` если есть, `Метрики:`.
2. **Канвасы и VPC** — у каждого Канваса есть `Ситуации:` и хотя бы одна VPC; в каждой
   VPC у Предложений проставлен `Развилка:` там, где был выбор; ERRC заполнено (Убрать /
   Снизить — текст из норм рынка; Поднять / Создать — ссылки на Результаты).
3. **Предпосылки**:
   - Sweep по `Влияет_на:` — каждая Предпосылка указывает реальное подмножество
     затронутых сущностей.
   - Добавляет scope-ставки (Тип: ставка, Пересмотр: мягкая), принятые неявно: фокус
     на нише, ценовой диапазон, географическое ограничение.
   - Пивоты (Тип: ставка, Пересмотр: твёрдая) — зафиксированы по ходу.
4. **Развилки** — sweep по `Влияет_на:`, проверка что закрытые Развилки имеют
   `Причина:` дословно из слов человека.
5. **Сигналы** — каждый факт, использованный в VPC (Работы / Альтернативы / УТП /
   Предложение / Результат / ERRC) и в экономике (CAC / LTV / Конверсия), подкреплён
   `Сигнал`. Добавляет недостающие.
6. **Эпистемические статусы** — агент сводит таблицу:
   - **Подтверждена Сигналами** — есть `Сигнал.Подтверждает`.
   - **Защищена твёрдой Премиссой** — твёрдая Предпосылка указывает на сущность через
     `Влияет_на:`.
   - **Гипотеза** — ни Сигналов, ни защиты. Эти узлы выносятся в отдельный список
     отчёта.
7. **Открытые вопросы** — собирает все `Неясно:` по Ситуациям и Канвасам в итоговый
   список (вывод в чат, не отдельный файл).
8. **План выхода в поле** — пробегает индекс Сигналов, находит противоречия (пары
   `Подтверждает [X]` + `Опровергает [X]`) и группирует план их закрытия по способу
   проверки:
   - **арбитраж эксперта** — для противоречий между кабинетными Сигналами;
   - **интервью с клиентом** — для пробелов про мотивацию, путь к решению, барьеры;
   - **тест-продажа** — для гипотез про готовность купить, которые непроверяемы
     кабинетно и не закрываются интервью.

   План не сохраняется в воркспейс как сущности — это операционный артефакт фазы.

**Итоговый отчёт агента (в чат):**

```
Воркспейс инициализирован:
- Юнитов: N
- Канвасов: N  (трипвайер / основа / развитие)
- Ситуаций: N  (фокусная: «…»)
- Переключений: N
- Сегментов / Работ / Результатов: N / N / N
- VPC / Предложений / Альтернатив: N / N / N
- Каналов / Доходов / Расходов: N / N / N
- Ресурсов / Активностей / Партнёров / Компонентов: N / N / N / N
- Связок / Петель: N / N
```

## Схема точек решения

```
Шаг 0   ─────────────────────────────────────────────────  агент
Шаг 1   ──────────────────────────  ◆ Предпосылки  ──────  человек (подтверждение)
Шаг 2   ──────────  ◆ Развилка / ◆ Пивот?  ──────────────  человек (если есть)
Шаг 3   ──  ◆ Развилка подхода Предложения  ──  ◆ Пивот?  ──  человек (по ходу)
Шаг 4   ──  ◆ Развилка формата / канала  ──  ◆ Пивот?  ──  человек (по ходу)
Шаг 5   ─────────────────────────────────────────────────  агент
Шаг 6   ─────────────────────────────────────────────────  агент
```

Развилки не накапливаются — каждая закрывается до того, как агент идёт дальше. Человек
никогда не получает пачку отложенных решений.

**Пивот возможен на любом шаге.** Признаки — в чеклисте Принципов. При пивоте часть
данных удаляется атомарным commit'ом, новый фокус закрепляется Предпосылкой (Тип:
ставка, Пересмотр: твёрдая) с `Влияет_на:`. История пивотов — в `git log`, не в
воркспейсе.

## Что получается в итоге

Готовая гипотеза продуктовой системы в pflow-воркспейсе:

- **Юнит** с портфелем из 1–3 Канвасов (лестница трипвайер → основа → развитие) и
  агрегатными метриками.
- **Ситуации** с Триггером, ЛПР, Срочностью и **Переключения** с 4 силами и Timeline —
  основа для контента, outbound и формулировки оффера.
- **Результаты** (ODI Outcomes) — наши метрики-ставки, на которые мы двигаем клиента.
- **VPC** с **ERRC** (Blue Ocean) — что отбрасываем из норм рынка, что поднимаем выше,
  что вводим впервые.
- **Канвасы** с Преимуществом, Каналами (CAC / LTV / Конверсия), типизированными
  Доходами и Расходами.
- **Ресурсы / Активности / Партнёры / Компоненты** — инфра, на которой строится
  выполнимость.
- **Связки / Петли** — где есть синергии между ступенями.
- **Сигналы** из открытых источников под каждое утверждение, с предикатами Подтверждает /
  Опровергает / Связан.
- **Закрытые Развилки** с `Влияет_на:` и `Причина:` дословно.
- **Предпосылки** — рыночные ограничения, scope-ставки и зафиксированные пивоты, все
  с `Влияет_на:`.
- **Список `Неясно:`** — открытые вопросы.
- **План выхода в поле** — что закрывать арбитражем эксперта, что интервью, что
  тест-продажей.

Это не финальная модель — первая итерация, готовая к выходу в поле.
