# Задачи продакта в ProductOps

ProductOps — это операционный слой продуктовой работы: рутинные циклы, которые держат продуктовую модель в актуальном состоянии и превращают разрозненные исследования, релизы и метрики в одну живую карту. Эта страница — каталог задач продакта по пяти фазам, с привязкой к сущностям DSL ProductFlow.

Каждая задача описана по схеме: **что продакт анализирует → зачем → какой полезный артефакт остаётся → какие дальнейшие действия запускаются**. Где возможно, артефакт — это конкретная сущность pflow/svcflow; связь модели и реальности проверяется встроенными warn/error LSP и MCP-инструментами.

> **Дерево аспектов как рабочая поверхность** — в [aspects.md](aspects.md).

## Карта фаз → сущности DSL

| Фаза | Что делает продакт | Сущности pflow | Сущности svcflow |
|---|---|---|---|
| **Discovery** | Понимает, кто и зачем | Сегмент, Работа, Переключение, Альтернатива, Сигнал | Персона, Контекст |
| **Strategy** | Решает, чем и как заработать | Канвас (Партнёр/Ресурс/Активность), VPC, Предложение, Юнит, Связка, Петля | — |
| **Delivery** | Доводит до операционной формы | VPC, Предложение, Компонент | Услуга, Обещание, Сценарий, Опора, Зависимость |
| **Growth** | Расширяет охват и удержание | Канал, Сигнал, Альтернатива | Апгрейд, Контекст |
| **Ops** | Поддерживает модель и команду | Сигнал, summaries-v2.jsonl | все svcflow-сущности |

## Дерево сущностей — рабочая поверхность ProductOps

Каждая задача продакта приземляется в Activity Bar → **ProductFlow → Дерево сущностей**. Дерево организовано в 4 секции — это и есть «утренний дашборд» продакта:

| Секция | Назначение | Что внутри |
|---|---|---|
| 🩺 **Состояние** | «Что нужно сделать сейчас» | Здоровье модели, Свежесть сигналов, Зрелость портфеля, Декларации без опоры, Опровергнутое и спорное, Hot spots |
| 🎯 **Стратегия** | «Куда смотреть наружу» | Карта рынка, Доказательная сила, Покрытие vs пробелы |
| 🔧 **Операция** | «Что улучшить внутри» | Готовность к запуску, Узкие места, Экономика и эффективность |
| 📚 **Справочник** | Навигация по типам | По одному аспекту на продуктовый вопрос: «Кто наш пользователь?», «Зачем ему это?», «Что мы продаём?» — всего ~24 |

Внутри каждого аспекта дерева продакт ожидает видеть: **(а)** список конкретных сущностей-items, **(б)** для glossary-аспектов — текстовую саммари с маркером свежести (fresh/stale/missing), **(в)** для state/strategy/operations — синтетический view (карточки, цепочки, чек-листы) без саммари, **(г)** badge на узле с количеством требующих внимания.

Ниже у каждой задачи строка **В дереве:** указывает конкретные аспекты, в которые она «смотрит».

## 1. Discovery — кто и зачем

### 1.1 Сегментация аудитории

- **Что анализирует:** интервью, заявки, отказы CRM, поведенческие когорты, демография ICP.
- **Зачем:** отделить группы, у которых принципиально разные Работы и Контексты — без этого решения уплывают в «средний по больнице».
- **Артефакт:** `Сегмент` с полями `Описание`, `Размер`, `Болевые точки`. В svcflow — `Персона` (конкретный носитель Работы) и `Контекст` (ситуация, в которой Работа активируется).
- **В дереве:** 📚 «Кто наш пользователь?» (список Сегментов с саммари) и 📚 «Кто конкретно покупает?» (Персоны) → 🎯 «Карта рынка» (Сегменты × Работы × Альтернативы — кого знаем, кого упускаем) → 🩺 «Декларации без опоры» (Сегменты без Сигналов / Работ).
- **Дальше:** для каждого нового Сегмента запускаются Discovery-интервью → появляются `Работа` и `Сигнал`; пустой Сегмент без связанной Работы LSP помечает как недомоделированный.

```pflow
Сегмент "SMB-разработчики 5-50 чел"
    Описание: Продуктовые команды без выделенного PM
    Размер: ~12 000 в RU
    Болевые точки: рассинхрон стратегии и бэклога
```

### 1.2 Jobs-to-be-Done

- **Что анализирует:** глаголы из интервью, формулировки «когда — хочу — чтобы», switch-моменты («перешли с / на»).
- **Зачем:** Работа — единица спроса; решения, отвязанные от Работы, не масштабируются.
- **Артефакт:** `Работа` с `Тип` (functional/social/emotional), `Триггер`, `Результат`. Switch-моменты — отдельная сущность `Переключение`.
- **В дереве:** 📚 «Зачем ему это?» (Работы) и 📚 «Откуда переходит, что мешает?» (Переключения) → 🎯 «Карта рынка» (видно, какие Работы вообще никем не покрыты Предложением) → 🩺 «Декларации без опоры» (Работы без Сигналов).
- **Дальше:** Работа становится якорем для `Предложение`; на каждой Работе живут метрики adoption — это будущие `Сигнал`.

```pflow
Работа "Согласовать продуктовый план с командой"
    Тип: functional
    Триггер: новый квартал / стратсессия
    Результат: общая карта приоритетов, не разваливающаяся через 2 недели
```

### 1.3 Анализ альтернатив

- **Что анализирует:** что Сегмент использует сегодня (включая Excel, Notion, ничего); причины удержания и оттока.
- **Зачем:** ценность измеряется относительно реальной альтернативы, не идеальной.
- **Артефакт:** `Альтернатива` с `Сильные стороны`, `Слабые стороны`, `Цена переключения`.
- **В дереве:** 📚 «Что клиент использует вместо нас?» (Альтернативы с саммари) → 🎯 «Карта рынка» (против каких Альтернатив играет каждый Сегмент) → 🎯 «Покрытие vs пробелы» (где Альтернатива закрывает Работу, а у нас Предложения нет).
- **Дальше:** слабые стороны конкурента превращаются в гипотезы для `Предложение`; цена переключения уходит в `Канал` (как снижать барьер).

### 1.4 Сигналы Discovery-фазы

- **Что анализирует:** глубинные интервью, поведенческая аналитика, NPS-опросы, custdev-формы.
- **Зачем:** подтвердить/опровергнуть гипотезу о Работе, Сегменте или Альтернативе до инвестиций в Delivery.
- **Артефакт:** top-level `Сигнал` с путь-ссылкой в полях `Подтверждает` / `Опровергает` (формат `Тип."имя"/Поле["элемент"]`).
- **В дереве:** 📚 «Откуда мы знаем?» (полный список Сигналов) → 🩺 «Свежесть сигналов» (что старше 6 мес — доказательная база теряет силу) → 🩺 «Опровергнутое и спорное» (где «за» и «против» одновременно) → 🎯 «Доказательная сила» (рейтинг Канвасов/Предложений/Сегментов по плотности и свежести Сигналов).
- **Дальше:** опровергающие Сигналы триггерят пересмотр Сегмента или Работы; подтверждающие — переход к Strategy.

```pflow
Сигнал "70% интервью упоминают рассинхрон стратегии"
    Категория: research
    Дата: 2026-04-12
    Источник: 14 custdev-интервью
    Подтверждает: Работа."Согласовать продуктовый план с командой"
```

## 2. Strategy — чем и как зарабатываем

### 2.1 Сборка Business Model Canvas

- **Что анализирует:** все Сегменты, их Работы, операционные ограничения, юнит-экономику.
- **Зачем:** Канвас связывает спрос (Сегмент/Работа) с поставкой (Партнёр/Ресурс/Активность) и деньгами (Расходы/Доход) — без этого продукт не выживает экономически.
- **Артефакт:** `Канвас` со всеми блоками BMC; `Партнёр`, `Ресурс`, `Активность`, `Отношения`, `Расходы`, `Доход` как самостоятельные сущности.
- **В дереве:** 📚 «Что мы предлагаем?» (Канвас) + соседние glossary-аспекты блоков BMC («С кем сотрудничаем?», «На каких ресурсах держимся?», «Что мы делаем регулярно?», «Где тратим?», «Как зарабатываем?») → 🎯 «Покрытие vs пробелы» (цепочки Сегмент → Канвас → Предложение → Услуга с подсветкой разрывов) → 🔧 «Экономика и эффективность» (P&L per Юнит — есть ли в Канвасе деньги).
- **Дальше:** дыры в Канвасе (Сегмент без Канала, Активность без Ресурса) превращаются в задачи; готовый Канвас — вход в портфельное планирование.

### 2.2 Портфельное планирование (Юниты и связки)

- **Что анализирует:** карту существующих и планируемых продуктов, их взаимные референсы, общую инфраструктуру.
- **Зачем:** одиночные продукты конкурируют, портфель усиливает друг друга через cross-sell, общие данные, общую аудиторию.
- **Артефакт:** `Юнит` (продукт-портфельная единица), `Связка` (направленная связь A→B), `Петля` (замкнутый цикл усиления).
- **В дереве:** 📚 «Как продукты связаны?» (Юниты) и 📚 «Как усиливают друг друга?» (Связки + Петли, объединены в один аспект) → 🔧 «Экономика и эффективность» (P&L по Юнитам — какой Юнит вытягивает портфель) → 🔧 «Узкие места» (есть ли SPOF между Юнитами через общие Опоры/Компоненты).
- **Дальше:** слабые Связки = кандидаты на интеграцию; обнаруженные Петли — основа growth-стратегии (см. фазу Growth).

```pflow
Связка "Free CLI → Cloud"
    Источник: Юнит."pflow CLI"
    Цель: Юнит."pflow Cloud"
    Тип: upsell
```

### 2.3 Выбор решений под Работы

- **Что анализирует:** Работы с подтверждёнными Сигналами, имеющиеся Компоненты, ресурсные ограничения команды.
- **Зачем:** Предложение — единица, которую команда реально строит; оно должно быть привязано к Работе и Сегменту, иначе нет адресата.
- **Артефакт:** `Предложение` с `Статусом` (idea/validating/building/shipped/sunset), `Покрытие` Сегментов и Работ, состав `Компонент`.
- **В дереве:** 📚 «Чем мы это решим?» (Предложения) → 🩺 «Зрелость портфеля» (карта фаз: идея / в работе / работает / устаревшее) → 🩺 «Hot spots» (Предложения, тянущие за собой цепочку проблем — куда инвестировать первый час) → 🎯 «Покрытие vs пробелы» (Работы без Предложения) → 🎯 «Доказательная сила» (рейтинг Предложений по плотности Сигналов).
- **Дальше:** Предложение в статусе `building` — вход в Delivery; `validating` требует подкрепления Сигналами; `sunset` запускает миграцию аудитории через `Апгрейд`.

### 2.4 Декомпозиция на компоненты и альтернативы реализации

- **Что анализирует:** какие переиспользуемые блоки уже есть, что нужно построить, что можно купить.
- **Зачем:** избежать дублирования между Предложениями одного портфеля.
- **Артефакт:** `Компонент` с `Тип` (data/api/ui/process), переиспользование через ссылки в нескольких Предложениях.
- **В дереве:** 📚 «Из каких модулей собираем?» (Компоненты) → 🔧 «Узкие места» (Компоненты-SPOF — один-на-многих Предложений, не-используется, в состоянии «нет») — это главное место для портфельных решений по компонентам.
- **Дальше:** Компонент с >1 потребителем = кандидат на платформенный roadmap; единственный потребитель — повод усомниться в выделении.

## 3. Delivery — операционная форма (svcflow)

### 3.1 Описание услуги и обещания

- **Что анализирует:** скоуп Предложения, ожидания клиента, SLA, измеримые исходы.
- **Зачем:** Услуга — то, что продаётся и обещается; без чёткого Обещания команда не знает, что считается «доставлено».
- **Артефакт:** `Услуга` с полем `Реализует: Предложение."..."` (cross-layer); `Обещание` с `Метрика`, `Целевое значение`, `Срок`.
- **В дереве:** 📚 «Что мы продаём?» (Услуги) и 📚 «Что клиент получает?» (Обещания) → 🔧 «Готовность к запуску» (карточки Услуг с галочками: Реализует / Работа / Цена / Обещания / Сценарии / Сигналы — чек-лист «что ещё нужно сделать») → 🎯 «Покрытие vs пробелы» (Предложения без привязанной Услуги).
- **Дальше:** Обещание без измеримой метрики = риск; продакт инициирует подбор метрики, иначе Услуга не может быть верифицирована.

```sflow
Услуга "Аудит продуктовой стратегии"
    Реализует: Предложение."Стратегический воркшоп"
    Сегменты: Сегмент."SMB-разработчики 5-50 чел"
    Обещание: Обещание."Карта приоритетов за 2 недели"
```

### 3.2 Проработка сценариев и опор

- **Что анализирует:** happy path, edge cases, точки отказа.
- **Зачем:** Сценарий описывает, как Услуга работает шаг за шагом; Опора фиксирует, на каком Ресурсе/процессе держится обещание (без явных опор обещание висит на честном слове).
- **Артефакт:** `Сценарий` с шагами и ответственными; `Опора` с `Обеспечивает: Ресурс."..."`.
- **В дереве:** 📚 «Как услуга работает?» (Сценарии) и 📚 «На чём держится обещание?» (Опоры) → 🔧 «Готовность к запуску» (Услуги без Сценариев / Опор) → 🔧 «Узкие места» (Опоры-SPOF, Опоры в состоянии «нет», неиспользуемые Опоры) → 🩺 «Декларации без опоры» (Обещание без обеспечивающей Опоры).
- **Дальше:** Опора без Ресурса в pflow-слое = warning на cross-layer уровне — повод либо завести Ресурс, либо снять Опору.

### 3.3 Карта зависимостей и контекстов

- **Что анализирует:** внешние блокеры, внутренние пререквизиты, контексты вызова услуги.
- **Зачем:** Delivery срывается на скрытых зависимостях; продакт фиксирует их явно, чтобы инженеры/RevOps/Legal видели приоритеты.
- **Артефакт:** `Зависимость` (от другой Услуги или внешнего поставщика), `Контекст` с `Альтернативы: Альтернатива."..."` (что клиент сделает, если Услугу не запустить).
- **В дереве:** 📚 «Что должно быть готово?» (Зависимости) и 📚 «В какой ситуации обращается?» (Контексты) → 🎯 «Карта рынка» (Контексты в связке с Альтернативами — где клиент уйдёт к конкуренту) → 🔧 «Готовность к запуску» (Услуги с висящими Зависимостями).
- **Дальше:** новая Зависимость с критическим статусом эскалируется владельцу; Контекст с сильной Альтернативой — повод усилить onboarding или сменить позиционирование.

## 4. Growth — расширение охвата и удержания

### 4.1 Анализ каналов

- **Что анализирует:** CAC по каналам, LTV/CAC, цикл сделки, конверсии воронки.
- **Зачем:** Канал — где Сегмент встречается с Предложением; неэффективный Канал тратит маркетинговый бюджет на нецелевую аудиторию.
- **Артефакт:** `Канал` с `Тип` (organic/paid/partner/community), привязка к Сегментам.
- **В дереве:** 📚 «Как доставим?» (Каналы) → 🔧 «Экономика и эффективность» (агрегаты Каналов в Юнитах — где деньги, где сливаем) → 🎯 «Покрытие vs пробелы» (Сегмент без Канала — формальный пробел).
- **Дальше:** Канал с плохой экономикой → гипотезы на оптимизацию (Сигнал «изменение CAC» → пересмотр Канала); кандидаты на новые Каналы вытаскиваются из интервью.

### 4.2 Retention и апгрейды

- **Что анализирует:** когорты, активация, отток, моменты «aha», точки шага вверх.
- **Зачем:** удержание дешевле привлечения; Апгрейд — формальный путь клиента вверх по портфелю.
- **Артефакт:** `Апгрейд` с `Источник: Услуга."..."`, `Цель: Услуга."..."`, `Триггер`.
- **В дереве:** 📚 «Куда клиент переходит дальше?» (Апгрейды) → 🩺 «Зрелость портфеля» (карта sunset→shipped Услуг — где обязательно нужен Апгрейд для миграции) → 🔧 «Экономика и эффективность» (Апгрейды как часть Юнит-связок).
- **Дальше:** низкий conversion на Апгрейде → пересмотр Обещания целевой Услуги; высокая активация без апгрейда → возможно, нужен новый промежуточный Юнит.

### 4.3 Мониторинг роста через Сигналы

- **Что анализирует:** weekly/monthly бизнес-метрики, продуктовые метрики, оттоки.
- **Зачем:** факты, на которые опирается стратегия, должны быть видимыми; иначе через квартал команда не помнит, почему приняла решение.
- **Артефакт:** регулярные `Сигнал` со ссылками `Связан` на Юнит/Предложение/Канал.
- **В дереве:** 📚 «Откуда мы знаем?» (Сигналы) → 🩺 «Свежесть сигналов» (что устарело — пора обновлять) → 🩺 «Опровергнутое и спорное» (где Сигналы расходятся со статусом Предложения) → 🎯 «Доказательная сила» (видно, какие Юниты держатся на свежих данных, какие — «на вере»).
- **Дальше:** опровергающий Сигнал на критическую гипотезу → созыв пересмотра Strategy-фазы; подтверждающий → масштабирование.

## 5. Ops — поддержание модели и команды

### 5.1 Гигиена модели (продуктовая база знаний)

- **Что анализирует:** актуальность Канваса, наличие пробелов в Сегментах/Работах, рассинхрон между pflow и svcflow.
- **Зачем:** модель устаревает быстро; рассинхронизированная карта хуже её отсутствия, потому что она дезинформирует.
- **Артефакт:** валидный starter-проект pflow, актуализированный `.pflow/summaries-v2.jsonl` (narrative-саммари по project и canvas-аспектам), отсутствие warn/error в Problems panel.
- **В дереве:** health-флаги на узлах (unfounded / orphans / broken-refs / canvas-skeleton / empty-fields / coverage / unit-economics / stale-signals) — это и есть «утренний дашборд» Ops; бейджи stale/missing на narrative-аспектах.
- **Дальше:** stale-маркер на summary (по `input_hash`) → продакт инициирует MCP-цикл `pflow_aspect_v2_status → pflow_aspect_v2_context → pflow_aspect_v2_save`; повторяющиеся пропуски в одном блоке → ретроспектива по процессу.

### 5.2 Ритуалы и ретроспективы

- **Что анализирует:** результаты квартала, отклонения от Обещаний, успешные/проваленные гипотезы.
- **Зачем:** ProductOps превращает разовые уроки в встроенные процессы.
- **Артефакт:** Сигналы-ретроспективы (`Категория: retro`), обновлённые `Описание` на затронутых сущностях, иногда — новый `Апгрейд` или `Зависимость`.
- **В дереве:** 🩺 «Опровергнутое и спорное» (где модель расходится с реальностью — кандидаты на ретро) → 🩺 «Зрелость портфеля» (что должно было быть `shipped`, но застряло) → 📚 «Откуда мы знаем?» (новые retro-Сигналы) → 🎯 «Доказательная сила» (как меняется после ретро).
- **Дальше:** изменение `Статус` Предложения; пересмотр Канваса; обновление starter-документов для команды.

### 5.3 Управление словарём и онбордингом

- **Что анализирует:** как новые члены команды читают модель, где спотыкаются, какие термины конфликтуют.
- **Зачем:** общий язык — главный множитель скорости в кросс-функциональной работе.
- **Артефакт:** обновления в `описание`-полях сущностей и summaries; правки в README/templates/starter, если возникают повторяющиеся вопросы.
- **В дереве:** вся секция 📚 **Справочник** как читаемая «вики продукта» — продуктовый вопрос → саммари → список сущностей. Метка fresh/stale/missing на узлах показывает, где знание актуально, где требует обновления. Для новичка дерево заменяет туровый онбординг: «прочитай 24 саммари в Справочнике — это и есть продукт».
- **Дальше:** регулярная сверка с командой раз в квартал; добавление новых примеров в `templates/starter/`.

## Как этот документ соотносится с инструментом

- Каждая задача оставляет след в `.pflow`/`.sflow`-файлах — это и есть «отчёт о ProductOps». Не нужно вести отдельный Notion-журнал.
- Пропущенная сущность (Сегмент без Работы, Услуга без Обещания, Опора без Ресурса) сразу видна как warn/error в редакторе и в MCP-инструменте `pflow_list`.
- Stale-саммари в дереве сущностей — индикатор, что фаза Ops отстаёт; cron-проверка `pflow_aspect_v2_status` встраивается в недельный ритуал продакта.
- Для запуска полного цикла рекомендуется начинать с [README проекта](../README.md) и проходить фазы 1→5 в указанном порядке, каждый раз сверяясь с этой картой.
